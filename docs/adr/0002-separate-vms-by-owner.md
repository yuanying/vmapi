# 0002. VM を持ち主で分ける

- Date: 2026-10-30
- Status: Accepted

## Context

vmapi は devbox proxy（dotfiles の ADR 0005・0007・0010）の後ろで公開する。proxy はブラウザを GitHub ログインで、API の利用者を Bearer token で検証し、検証した利用者の名前を `X-Devbox-User` に入れてバックエンドへ渡す。

利用者は複数いる。Penelope が検証のために作った VM を、手元の pi のエージェントが別の作業の中で消してしまう、という事故は防ぎたい。一方で、次の事実がある。

- Bearer token は `devbox-proxy token --service vm --user <名前>` で発行する。名前は `viewers` と照合されず、`api.key` を読める人は誰の名前でも token を作れる（dotfiles ADR 0010）。
- devbox の apps のネットワーク（`v6net`）に居るコンテナは、proxy を経ずにバックエンドへ届き、`X-Devbox-User` を自分で付けられる（dotfiles ADR 0012 の改訂）。

つまり `X-Devbox-User` は「この名前を名乗っている」以上のことを保証しない。

## Decision

**`X-Devbox-User` の値を VM の持ち主とし、利用者は自分が持ち主の VM だけを一覧・操作できる。設定で管理者に挙げた名前（`yuanying`）は、すべての VM を一覧・操作できる。**

- **これは事故を防ぐための線引きであり、悪意への防御ではない。** 他人の名前を名乗る利用者を止める手段を vmapi は持たない。持たないことを前提に、この線引きより強い保証が要る用途には vmapi を使わない。
- **利用者を登録する仕組みは作らない。** vmapi は利用者の一覧を持たない。初めて見る名前でも、その名前の持ち主として VM を作れる。エージェントは vmapi にも proxy の `viewers` にも登録せず、`devbox-proxy token --service vm --user <名前>` で発行した token の名前がそのまま持ち主になる。今の名前は Penelope が `penelope`、手元の pi が `pi` である。管理者の `yuanying` の token はエージェントに持たせない。
- **`X-Devbox-User` の無いリクエストは `401` で拒否する。** proxy が `auth: required` で転送していれば必ず付くので、無いのは proxy を経ていないか、設定を誤っているかのどちらかである。
- **他人の VM は、存在しないものとして扱う。** 取得・操作は `404` を返す。一覧には出さない。ただし名前は全体で一意なので（[[0003]]）、作成のときの `409` から、その名前の VM が誰かにあることは分かる。線引きの目的に照らして、それは許す。
- **管理者の絞り込み。** 管理者の一覧は既定ですべての VM を返し、持ち主の名前で絞り込める。管理者でない利用者が自分以外の持ち主で絞り込むと `403` を返す。黙って空の一覧を返すと、指定を誤ったことに気づけないからである。
- **管理者でも持ち主は自分になる。** 管理者が作った VM の持ち主は管理者であり、他人の名前で作る手段は設けない。
- **持ち主は作成のときに決まり、変えられない。** 持ち主を移す API は作らない。

### 前提

この線引きは、vmapi に届くリクエストがすべて proxy を経ていることを前提にする。vmapi のコンテナはホストのポートを公開せず、devbox の apps のネットワークにだけつなぐ（[[0008]]）。ホストのファイアウォールは apps のポートを LAN に閉じる（dotfiles ADR 0012）。

それでも、同じネットワークに居るコンテナからは proxy を経ずに届く。dotfiles ADR 0012 が言うとおり、そこで付いた `X-Devbox-User` は何の証明にもならない。この経路を塞ぐことは vmapi の範囲の外であり、塞がれていないことを前提に、上の「悪意への防御ではない」を置いている。

## Consequences

- 利用者を足すのに vmapi の変更も設定も要らない。token を発行すれば、その名前の利用者になる。
- 名前の綴りを誤った token で作った VM は、その誤った名前の持ち主になる。直すには管理者が消して作り直す。
- 管理者の名前を名乗れば、すべての VM を消せる。`api.key` の読める範囲と、apps のネットワークに居るものが、vmapi の実際の信頼の範囲である。
- 持ち主の判定はリクエストの名前と metadata の持ち主の比較だけなので、libvirt を偽物に差し替えたテストで確かめられる。

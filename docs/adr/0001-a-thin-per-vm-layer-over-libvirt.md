# 0001. libvirt の上に VM 単位の薄い層を置く

- Date: 2026-10-30
- Status: Accepted

## Context

boucherie（devbox のホスト）の `qemu:///system` では、Kubernetes の dev/test クラスタなどの VM が動いている。これまでは `k8s-env` と `porkadot-dev` の shell スクリプトが env ファイルを読んで `virt-install` を呼び、cloud-init の ISO を `genisoimage` で作っていた。IP は env ファイルに固定で書いていた。

この形には二つの不便がある。

- **サンドボックスの中のエージェントは libvirt のソケットに触れない。** VM を作るたびに、人間がサンドボックスの外での実行を許可している。
- **誰が何のために作った VM かが残らない。** IP の割り当ても人間が env ファイルを見て決めている。

利用者はエージェント（運用係の Penelope、手元の pi ほか）と人間（ブラウザとシェル）の両方であり、後から増える。既存のスクリプトとの互換は求められていない。

## Decision

**vmapi は、libvirt の上に置く VM 単位の薄い HTTP API とする。** 扱うのは個々の VM の作成・一覧・取得・起動・停止・削除と、そのスナップショット、それに選べる OS イメージの一覧だけである。

- **クラスタやテンプレートは扱わない。** 何台の VM をどう組み合わせてクラスタにするかは、呼ぶ側（スクリプト、エージェント）の仕事とする。vmapi に「クラスタ」のリソースは作らない。
- **vmapi が作った VM だけを扱う。** 既存の VM（スクリプトで作ったもの）は一覧にも出さず、操作もしない。見分け方は [[0003]] で決める。既存の VM は vmapi と併存させ、片付けは別に行う。
- **作成は同期で完了させる。** ドメインの define と start が済んだら `201` と払い出した IP を返す。ゲストの OS が使えるようになったか（ssh できるか、cloud-init が終わったか）は呼ぶ側が確かめる。準備完了の通知は今は作らない（[[0007]]）。
- **入口は三つ、契約は一つ。** JSON の HTTP API を OpenAPI（`api/openapi.yaml`）で定め、CLI の `vmctl`、一覧と簡単な操作だけの画面（Go のテンプレートで 1 ページ）、codemode の道具（dotfiles の pi extension）は、どれもその API を呼ぶ。作成は API・CLI・codemode から行い、画面からは行わない。
- **実装は Go、libvirt との通信は `digitalocean/go-libvirt` を使う。** pure Go で、libvirt のソケットに RPC で話す。cgo も libvirt のクライアントライブラリも要らないので、静的なバイナリになり、`make test` が Go のツールチェーンだけで通る。

## Consequences

- vmapi が持つ概念は「VM」「スナップショット」「イメージ」「利用者」の四つにとどまる。クラスタを組むスクリプトは vmapi の上に書き直すことになる。
- libvirt を直接触らずに VM を作れるので、エージェントはサンドボックスの外での実行を頼まずに VM を扱える。代わりに、vmapi の権限の線引き（[[0002]]）と、vmapi を動かす場所の権限（[[0008]]）が重要になる。
- 作成が同期なので、イメージの初回取得を含む作成のリクエストは長くかかることがある（[[0004]]）。呼ぶ側はタイムアウトを長めに取る。
- 「準備完了」を vmapi が知らないので、呼ぶ側はポーリング（ssh の接続を試すなど）を自分で書く。通知が要るようになったら、VM の状態にフィールドを足す形で後から加えられるよう、応答の形を保つ（[[0007]]）。
